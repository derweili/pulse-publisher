# mOS integration readiness audit — pulse-publisher

Audited 2026-08-13, repo `pulse-publisher` at branch `claude/publisher-demo-features-plan-ahrthc`. Read-only audit; no code changed.

Two constraints framed every finding below:
1. mOS can only manipulate what's addressable by a stable CSS selector in server-rendered HTML — hydration-only content is invisible to `HTMLRewriter`.
2. The origin response is cached and shared across readers — anything reader-specific rendered server-side either fragments the cache or leaks between readers.

## 2. Deployment and Worker config

**`wrangler.toml`** (full contents):

```toml
#:schema node_modules/wrangler/config-schema.json
name = "pulse-today"
main = "./dist/_worker.js/index.js"
compatibility_date = "2026-08-12"
compatibility_flags = ["nodejs_compat"]

[assets]
directory = "./dist"
binding = "ASSETS"
```

No `[[kv_namespaces]]`, `[[d1_databases]]`, `[[durable_objects]]`, no `[observability]`, no `routes`/`custom_domain` entries, no `[[env.*]]` blocks. There is exactly one environment (production, implicit/default). No `run_worker_first` setting — this key doesn't apply here anyway since it's for the `[assets]` config *when a Worker sits in front of static assets*; here the Worker *is* the entrypoint that handles all routing (see below).

**`astro.config.mjs`** (full contents):

```js
import { defineConfig } from 'astro/config';
import react from '@astrojs/react';
import tailwindcss from '@tailwindcss/vite';
import clerk from '@clerk/astro';
import cloudflare from '@astrojs/cloudflare';

export default defineConfig({
  output: 'server',
  adapter: cloudflare({
    platformProxy: { enabled: true },
  }),
  integrations: [clerk(), react()],
  vite: {
    plugins: [tailwindcss()],
  },
});
```

- **Output mode:** `server` (full SSR), not `static` and not hybrid. Every route renders per-request unless a page explicitly opts out with `export const prerender = true` — a repo-wide grep found **zero** such flags. So every route in §3 is SSR.
- **Adapter:** `@astrojs/cloudflare` builds a Worker at `dist/_worker.js/index.js` (matches `wrangler.toml`'s `main`). This is a build artifact generated by the Astro Cloudflare adapter, not a hand-written Worker file — there is no custom Worker entrypoint in the repo to hook into. Whoever wires up mOS either edits Astro/adapter config to inject something into that generated Worker, or — more likely given the "reverse-proxy Worker in front" model — writes an entirely separate Worker and leaves this one untouched.
- **`platformProxy: { enabled: true }`** — dev-only; makes `astro dev` read Worker bindings/secrets from `.dev.vars`, matching prod's `Astro.locals.runtime.env`. Not relevant to the deployed proxy.
- **No Workers Cache API usage** (`caches.default`, `context.waitUntil` for cache warming, etc.) anywhere in `src/`. No `cache: { enabled }` config for `[assets]` in `wrangler.toml` — the default Workers static-assets caching behavior applies to `./dist` files only; it says nothing about SSR page responses, which the app never sets `Cache-Control` on (confirmed by repo-wide grep — see §8).
- **Custom domains / routes:** none declared in `wrangler.toml`. UNKNOWN — would need to check the Cloudflare dashboard for `pulse-today`'s actual bound routes/custom domains, since none are IaC-tracked here.
- **Deploys:** two paths, both calling the same underlying command:
  1. `.github/workflows/deploy.yml` — triggers on push to `main` or manual `workflow_dispatch`. Runs `npm ci`, `npm run build` (with `PUBLIC_CLERK_PUBLISHABLE_KEY`, `PUBLIC_SANITY_PROJECT_ID`, `PUBLIC_SANITY_DATASET`, `PUBLIC_SANITY_API_VERSION` injected as build-time secrets), then deploys via `cloudflare/wrangler-action@v4` using `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` GitHub secrets. Uses **Node 20** in CI, vs. Node 22 installed locally — worth aligning before any proxy work touches the build.
  2. Manual: `npm run deploy` → `npm run build && wrangler deploy`.
  - `SANITY_API_READ_TOKEN` is set once per environment via `wrangler secret put` (or the dashboard), not part of either deploy path — it's a Worker runtime secret, not a build-time env var, because Sanity is queried live per request (see §7).

## 4. Rendering and hydration

**React islands** (`@astrojs/react`, React 19.2.8):

| Component | Hydration directive | What it does |
|---|---|---|
| `SearchTrigger.tsx` (in `Header.astro`) | `client:idle` | Modal search UI; fetches `/search-index.json` lazily on open, scores client-side |
| `MobileMenu.tsx` (in `Header.astro`) | `client:idle` | Off-canvas nav drawer, portal to `document.body` |
| `ForYouRail.tsx` (in `index.astro`) | `client:visible` | Reads `localStorage` reading history, fetches `/api/for-you.json`, renders a "For You" grid |
| `Comments.tsx` (in `articles/[slug].astro`) | `client:idle` | **Entirely fake** — hardcoded `FAKE_COMMENTS` array, no backend. Not a real integration point |
| `SavedArticles.tsx` (in `saved.astro`) | `client:load` | Reads Clerk user's `unsafeMetadata.savedArticleSlugs`, fetches `/api/saved-articles.json` |

- **`<ClientRouter />` / view transitions:** not used anywhere. Repo-wide grep for `ClientRouter` and `transition:` found nothing. Full page navigations only.
- **`prefetch`:** not enabled in `astro.config.mjs` (no `prefetch: true`/config block), and no `data-astro-prefetch` attributes found in templates.
- **No client-side routing or content-swapping** of any kind — this is a traditional multi-page SSR app. Good news for a reverse proxy: every navigation is a fresh HTTP request the proxy will see.
- **Content that only exists post-hydration:**
  - `ForYouRail` — the entire "Just for you" homepage section is empty markup server-side (`<div aria-hidden="true">` or `null`) until the client fetch resolves. mOS cannot see or gate this content server-side at all.
  - `SavedArticles` — the `/saved` page body is a loading-state string server-side; actual content only exists client-side, scoped to one signed-in reader, and is never in the cached HTML.
  - `Comments` — fake, static, identical for every reader; hydrates but renders the same content every time.
  - The Clerk `<Show>` control (`Header.astro`, `SaveButton.astro` via the `$userStore`/`$clerkStore` nanostores) — see §6, this one is subtler: both signed-in and signed-out branches **are** present in the server HTML, just `hidden`-toggled client-side. Not "hydration-only" in the usual sense, but also not something a naive `HTMLRewriter` selector search would find meaningful without knowing this pattern.

## 5. The mOS surface inventory

### Article body wrapper and paragraph structure

Source: `src/pages/articles/[slug].astro:158-166`, rendered via `src/components/portable-text/{PortableText,Block}.astro`.

```html
<div class="container-page mt-10 grid grid-cols-[1fr_320px] items-start gap-12 max-[960px]:grid-cols-1 max-[960px]:gap-8">
  <div class="w-full max-w-[680px]">
    <!-- AdSlot: in-article-1 -->
    <p class="my-[1.2em] text-[calc(1.125rem*var(--reading-scale,1))] leading-[1.7] text-ink-2 max-sm:text-[calc(17px*var(--reading-scale,1))]">…</p>
    <h2 class="mt-[1.8em] mb-[0.6em] text-[calc(1.5rem*var(--reading-scale,1))] tracking-[-0.01em]">…</h2>
    <blockquote class="my-[1.8em] border-l-4 border-primary pl-6 …">…</blockquote>
    <!-- AdSlot: in-article-2 -->
    <p class="my-[1.2em] …">…</p>
    …
  </div>
</div>
```

- The body comes from **Sanity Portable Text** (`article.body`, schema in `studio/schemaTypes/objects/blockContent.ts`): an array of `block` (paragraph/`h2`/`blockquote`/lists, with inline `strong`/`em`/`link` marks), `imageBlock`, and `videoEmbed` members. `Block.astro` renders each text block; `PortableText.astro` groups consecutive list items.
- **Every paragraph, heading, and quote gets the same handful of Tailwind utility classes** — no `id`, no `data-*` index, no distinguishing attribute between paragraph 1 and paragraph 30. Multiple blocks can share identical class strings.
- **The app itself already splits the body at the midpoint** for ad placement: `articles/[slug].astro:44-47` does `Math.floor(blocks.length / 2)` and renders `firstHalf`/`secondHalf` around a second `<AdSlot>`. This split is by **block array index**, computed server-side before rendering — it is not expressed in the HTML output at all (no wrapper marks where the split happened). A rewriter has no way to locate it after the fact.
- **Verdict: `HTMLRewriter` cannot reliably find "the end of paragraph 3" today.** Nothing distinguishes one `<p>` from another except DOM position, and `HTMLRewriter`'s selector model (CSS-like, streaming, no nth-child-of-type-among-siblings-with-different-tag-names counting) can't safely count mixed-tag siblings, especially once ads/images are interleaved. **Needs a `data-mos-block` (or similar) index attribute added to `Block.astro`/`PortableText.astro` at render time** — cheap, since the index is already known during the `.map()` in `PortableText.astro:16`.

### Premium article layout

Source: `src/pages/articles/[slug].astro:42, 107-118` and `ArticleCard.astro:24,35-37,70-72,100-102,124-126,170-193`.

- `isPremium = article.premium ?? false` — a single boolean field on the Sanity `article` schema (`studio/schemaTypes/documents/article.ts:103-110`). No other access-control field exists on the article, section, or any other schema (checked all 5 document types and all 8 object types in `studio/schemaTypes/`).
- **Critical finding: premium content is NOT withheld server-side today.** When `isPremium` is true, the page renders an extra gold banner block:
  ```html
  <div class="bg-premium-gold text-[#2a1d00]">
    <div class="container-page flex flex-wrap items-center gap-4 py-3">
      <span class="… bg-[#2a1d00] … text-premium-gold …">PULSE+ Premium</span>
      <span class="…">This is in-depth reporting for subscribers. Unlock the full archive with PULSE+.</span>
      <a href="/subscription" class="…">Subscribe</a>
    </div>
  </div>
  ```
  …but the **full `article.body` Portable Text still renders in full**, unconditionally, right below it. There is no truncation, no server-side gating, no `hidden` attribute on the back half of the content. Anyone — logged in or not, paying or not — gets the complete article HTML today.
- On listing cards (`ArticleCard.astro`), premium articles just get a `<span>Premium</span>` badge overlay and (for the dedicated `variant="premium"` card) a dark themed card — cosmetic only, same underlying link to the full, ungated article.
- **This means mOS is not "tightening an existing paywall" — it is introducing the paywall from scratch.** The `isPremium` boolean is a reasonable decision-input signal, but the actual withholding of content (or replacing it with a teaser + registration/paywall UI) is entirely mOS's job to perform via `HTMLRewriter`, using the per-block index attribute recommended above to decide where to cut.

### Ad placeholders

Source: `src/components/AdSlot.astro`, used at 13 call sites across `Layout.astro` (via `StickyAd.astro`) and every listing/article page.

Every ad slot shares one wrapper shape:
```html
<aside
  class="flex w-full items-center justify-center mx-auto …"
  data-ad-slot="leaderboard-top"
  role="complementary"
  aria-label="Advertisement"
>
  <div class="ad-inner flex max-w-full flex-col … rounded-lg border border-dashed …">
    <span class="…">Advertisement</span>
    <span class="…">leaderboard-top</span>
    <span class="font-mono text-xs text-ink-5 opacity-80">728px × 90px</span>
  </div>
</aside>
```

- **`data-ad-slot="<slot-name>"` is already a stable, purpose-built selector** — every instance is uniquely named (`leaderboard-top`, `in-article-1`, `in-article-2`, `mpu-rail`, `native-in-feed`, `sticky-footer`). This is the one surface in the whole repo that's already `HTMLRewriter`-ready with zero changes needed.
- Slot inventory: `leaderboard-top` (every listing/article page top), `in-article-1`/`in-article-2` (article body, currently at the fixed body-midpoint split described above), `mpu-rail` (article/section/author sidebar), `native-in-feed` (homepage/section/tag/author feeds), `sticky-footer` (global, via `StickyAd.astro`, client-toggled visible/hidden with an `IntersectionObserver` — the wrapping `[data-sticky-ad]` div is server-rendered, but its visibility is 100% client-driven via `data-visible` + CSS; an ad-free rewrite would need to strip or neutralize this client script too, not just delete the DOM node).
- **Verdict: ready today.** `[data-ad-slot]` selectors are stable and semantic. Removing/replacing ad slots for an ad-free experience is a matter of matching this one attribute.

### Header auth area (signed-in vs signed-out)

Source: `src/components/Header.astro:55-67`, using `@clerk/astro/components`' `<Show>`.

```html
<clerk-show data-when="signed-out" class="">
  <div hidden data-clerk-control-slot-default>
    <button class="… SignInButton …">Sign in</button> <!-- approximate -->
  </div>
  <div hidden data-clerk-control-slot-fallback></div>
</clerk-show>
<clerk-show data-when="signed-in" class="">
  <div hidden data-clerk-control-slot-default>
    <a href="/saved">Saved</a>
    <!-- <UserButton /> -->
  </div>
  <div hidden data-clerk-control-slot-fallback></div>
</clerk-show>
```

This is the most important structural finding for §6/§8: **because this repo has no server-side Clerk auth wired up** (see §6), `<Show>` always resolves to its **client-side-rendered variant** (`ShowCSR.astro`), which server-renders *both* branches into the HTML, both `hidden`, inside a `<clerk-show data-when="…">` custom element, and a client-side script (`ClerkShow` custom element handler, bundled from `@clerk/astro`) reveals the correct one once Clerk's session state resolves in the browser. **The server-rendered HTML is therefore identical for every reader regardless of auth state** — good for cache safety, bad if mOS wants to *server-side* rewrite based on signed-in/out (there's no server signal to key off; the decision has to happen client-side or mOS has to inject its own server-side auth read, which this app doesn't do). `data-when="signed-in"`/`data-when="signed-out"` on `<clerk-show>` are stable selectors if mOS only needs to *find* these regions, but rewriting their content usefully still requires either duplicating Clerk's client reveal logic or making a fresh server-side auth determination.

### Bookmark controls

Source: `src/components/SaveButton.astro`, used on every `ArticleCard` variant and the article detail header.

```html
<button
  type="button"
  class="inline-flex justify-center items-center gap-1.5 rounded-full border border-border …"
  data-save-button
  data-slug="some-article-slug"
  aria-pressed="false"
  aria-label="Save article for later"
>
  <svg data-save-icon-outline>…</svg>
  <svg class="hidden" data-save-icon-filled>…</svg>
</button>
```

- `[data-save-button]` + `data-slug` is a stable selector, present identically for every reader server-side (the button always initially renders "not saved" — `aria-pressed="false"`, outline icon shown). Actual saved-state is applied client-side via a script reading Clerk's `user.unsafeMetadata.savedArticleSlugs` and toggling `hidden`/`aria-pressed` per button (`SaveButton.astro:29-84`). **No server-side variance, safe for shared caching, but the "saved" visual state itself is invisible to any HTML rewriting done server-side** — it doesn't exist until the client re-derives it from Clerk. Not typically an mOS concern (bookmarking isn't a monetization surface) but noting it since it was in the audit's ask list.

### "Premium" badge/marker on cards and listings

Source: `ArticleCard.astro` — badge markup differs slightly by variant, all built from the same `isPremium` boolean:

- `variant="hero"`: `<span class="absolute top-4 right-4 … bg-premium-gold …">Premium</span>` (only rendered `{isPremium && (...)}` — i.e., **absent from the DOM entirely** for non-premium cards, not just hidden)
- `variant="default"`/`"compact"`/`"list"`: same conditional pattern, different position classes
- `variant="premium"` (dedicated card used only in the homepage PULSE+ section): premium badge is unconditional since every card in that section is premium by construction

No `data-premium` attribute exists on the badge or the card root — only the conditional presence/absence of a `<span>Premium</span>` with Tailwind utility classes distinguishes state. **Would need a `data-premium="true"` attribute on the article `<article>`/`<a>` root** (not just the inner badge span) if mOS wants a single reliable selector to detect "this card links to premium content" across all five `ArticleCard` variants, `SavedArticles.tsx`, and `ForYouRail.tsx` (the latter two — note — **don't render a premium badge at all today**, a gap worth flagging to content/product even outside the mOS integration).

## 6. Clerk integration

- **SDK:** `@clerk/astro` v4.0.11 (installed; see §1). This wraps `@clerk/clerk-js` for the browser and (per its `package.json`) depends on `@clerk/backend` — but that backend dependency is not invoked anywhere in this app's own code.
- **Server-side vs. client-side usage: entirely client-side.** Confirmed by three independent signals:
  1. `.env.example` states outright: *"This is the site's only Clerk build/runtime dependency: the site is fully static… so auth runs entirely client-side via Clerk's browser SDK — no `CLERK_SECRET_KEY` is needed."* (Note: this comment is stale in one respect — the site is **not** fully static, it's SSR per `astro.config.mjs`'s `output: 'server'` — but its conclusion about Clerk being client-only auth is independently verified below.)
  2. Repo-wide grep for `clerkMiddleware`, `@clerk/astro/server`, `Astro.locals.auth`, `locals.auth` in `src/` returns **zero matches**. No `src/middleware.ts` exists at all.
  3. Inspected `@clerk/astro`'s own integration code (`node_modules/@clerk/astro/dist/index.js`) — its `astro:config:setup` hook only calls `injectScript` (client-side script injection for `before-hydration`/`page` lifecycle), never registers Astro middleware. ## 7. Sanity integration

- **Client config** (`src/lib/sanity/client.ts`): `createClient({ projectId, dataset, apiVersion, token, useCdn: false, perspective: "published" })`. `useCdn: false` means **every** query hits Sanity's live (non-CDN) API directly — no Sanity-side response caching. `perspective: "published"` means drafts are never returned. `projectId`/`dataset`/`apiVersion` come from build-time `PUBLIC_*` env vars (inlined via Vite); `token` (`SANITY_API_READ_TOKEN`) comes from the Worker's per-request runtime env (`Astro.locals.runtime.env`), because the dataset is private and every request needs read auth. A fresh `SanityClient` is constructed **per request** (not a module-level singleton) specifically so it can pick up that per-request runtime secret correctly under Cloudflare's isolate model.
- **Live vs. CDN:** live, uncached, per-request — this is deliberate (per code comments) so Studio edits appear immediately with no rebuild. It also means every page load, including ones a reverse proxy might want to cache, does a real Sanity API round-trip today unless something (mOS's proxy, Workers Cache, etc.) caches the *rendered HTML* output.
- **Schema — Article** (`studio/schemaTypes/documents/article.ts`): `title` (string), `slug` (slug), `dek` (text, standfirst/meta-description fallback), `section` (reference→section, required), `authors` (array of reference→author, required, min 1), `hero` (image with required `alt`, hotspot), `body` (Portable Text, required, min 1 block), `publishedAt` (datetime), `readTime` (number), `tags` (array of string), **`premium` (boolean, default false — the only access-level field, see §5)**, `featured` (boolean), `trendingRank` (number, optional), `seo` (object — metaTitle/metaDescription/ogImage, per `objects/seo.ts`, not fully expanded here but standard).
- **Schema — Section** (`studio/schemaTypes/documents/section.ts`): `title`, `slug`, `tagline`, `accentColor` (hex, validated), `order` (number), `seo`.
- **Schema — Author** (`studio/schemaTypes/documents/author.ts`): not fully read line-by-line in this pass, but queries (`queries.ts:73-97`) show fields `name`, `slug`, `role`, `bio`, `avatar`, `twitter`, `seo`.
- **Schema — siteSettings** (singleton, `studio/schemaTypes/documents/siteSettings.ts`): `title`, `tagline`, `logo`, `defaultSeo` (required), `mainNav` (array of navLink), `footerLinkGroups`, `socialLinks`, `copyrightText`, `breakingNews` (object: `active` boolean, `headline`, `href`) — the breaking-news banner is toggled live from Studio with no redeploy, per its own description field.
- **Schema — blockContent** (`studio/schemaTypes/objects/blockContent.ts`, used for `article.body` and `liveBlog.entries[].body`): native Portable Text `block` (styles: normal/h2/blockquote; lists: bullet/number; marks: strong/em decorators, `link` annotation with `href`+`newTab`), plus custom `imageBlock` and `videoEmbed` array members.
- **Access-level/premium/paywall fields, specifically:** **only `article.premium: boolean`.** No field for "free preview paragraph count," no per-block access markers, no subscription tier enum, nothing on `section` or `siteSettings` either. If mOS's Decision API or the proxy needs finer-grained control (e.g. "first N paragraphs free"), that's either a hardcoded rule in the proxy/mOS config, or a schema change to `article.ts`/`blockContent.ts` this audit did not find any groundwork for.
- **Query construction:** GROQ queries live in one file, `src/lib/sanity/queries.ts`, using `defineQuery` from the `groq` package (enables typed results via a generated `sanity.types.ts` — see `npm run studio:typegen`). List queries share a `cardProjection` fragment that explicitly **excludes** `body` (keeps list payloads small) and **includes** `premium`. The single article-detail query (`articleBySlugQuery`) fetches the full `body` array unconditionally, regardless of `premium` — reinforcing the §5 finding that premium gating isn't applied at the data layer either; the full body is always fetched and always rendered.
- **Caching/revalidation:** none — see "Live vs. CDN" above. No ISR, no ETags, no stale-while-revalidate logic found.
- **Webhooks:** repo-wide search for "webhook" in both `src/` and `studio/` returned zero matches. None configured in-repo. UNKNOWN — would need to check the Sanity project dashboard for any webhook configured outside the codebase (e.g. a Studio deploy hook or an external cache-purge webhook).

## 8. Caching and cookie behaviour

- **Cookies set by this app's server code:** none. Repo-wide grep for `Set-Cookie`, `cookies.set`, `Astro.cookies` across `src/` returned zero matches. All app-level "persistence" is `localStorage`/`sessionStorage`, entirely client-side:
  - `pulse-cookie-consent` (`CookieConsent.astro`) — localStorage
  - `pulse-reading-history` (`ReadingHistoryTracker.astro`, read by `ForYouRail.tsx`) — localStorage
  - `pulse-reading-scale` (`ReadingControls.astro`) — localStorage
  - `ad-dismissed-sticky-footer` (`StickyAd.astro`) — sessionStorage
  - `breaking-dismissed-<headline>` (`BreakingNewsBanner.astro`) — sessionStorage
  - Clerk's own session cookies — set by Clerk's client-side SDK, not by this app's code (see §6)
- **`Cache-Control` headers:** none set anywhere in `src/` (repo-wide grep for `Cache-Control`/`cacheControl`/`s-maxage`/`max-age` returned zero matches in application code). Every response — HTML pages and the JSON API endpoints alike — relies entirely on Cloudflare/browser defaults for an uncached-by-default dynamic response. **This is actually good news for a caching proxy: there's no existing `Cache-Control: private` or `no-store` the proxy would need to override or fight.**
- **What makes a response reader-specific, today:** based on everything above, **nothing renders server-side that varies by reader.** Every page:
  - Queries Sanity fresh per request, but Sanity content is the same for every reader (no per-reader Sanity query params anywhere)
  - Renders both Clerk auth branches unconditionally, client-toggled (§6)
  - Never reads a cookie or any reader-identifying header to alter its HTML output
  - Defers all genuinely reader-specific rendering (`SavedArticles`, `ForYouRail`, saved-state on `SaveButton`) to client-side `fetch()` calls against `/api/*.json` endpoints, which themselves take reader-specific state (slugs, Clerk user metadata) only as explicit query params/client requests — not from server-side session state
  
  **In short: this app is already cache-safe as-is.** The one thing that will genuinely change this is mOS itself — once mOS's `HTMLRewriter` starts injecting reader-specific paywall/registration-wall markup into the response *before* the shared cache layer, the proxy (not this app) becomes the thing responsible for either caching pre-personalization and personalizing after cache, or fragmenting cache by decision-outcome (e.g. cache key includes "paywalled" vs. "free" vs. "registered"), or not caching HTML at all and only caching Sanity-layer data. That architectural decision sits entirely in mOS's design, not this repo — but it's worth stating plainly since the audit prompt raised the concern: **this repo isn't the source of a cache-fragmentation problem; if there is one, it'll be introduced by the proxy's personalization step, and needs a caching strategy on the mOS side.**
- **Geo/device/header-based variance:** none found. No `Accept-Language` branching, no `CF-IPCountry` reads, no User-Agent sniffing server-side (only a client-side `max-[…]` CSS breakpoint responsive design, which is not server variance).

## 9. Readiness assessment

### Blockers — must change before the proxy can work at all

1. **Article body has no per-paragraph addressability.** Every `<p>`/`<h2>`/`<blockquote>` in the article body shares interchangeable classes with no `data-*` index. `HTMLRewriter` needs a stable per-block hook to implement "free preview through paragraph N, paywall after." **Fix:** add a `data-mos-block="<index>"` (or similar) attribute in `Block.astro` and `ImageBlock.astro`/`VideoEmbed.astro`, using the index already available in `PortableText.astro`'s `.map()`.
2. **No server-side entitlement signal exists for mOS to key off, and no server-side content withholding exists to piggyback on.** `article.premium` is a boolean the Decision API can read from Sanity, but this repo renders full article bodies unconditionally regardless of that flag — mOS is authoring the withholding logic from scratch, not adjusting an existing gate. This isn't necessarily a blocker to *starting* the integration, but it changes the shape of the work: mOS needs its own truncation/replacement logic keyed to the block-index attribute in #1, since there's no existing "free preview vs. gated" HTML boundary to detect.
3. **No `data-premium` marker on article-card roots** (`ArticleCard.astro` and its two React counterparts `SavedArticles.tsx`/`ForYouRail.tsx`, the latter two currently missing premium badges *entirely*). If mOS needs to detect "this card is premium" on listing pages (e.g. to add its own badge, or gate click-through), there's no single reliable selector today.

### Should change — will cause pain if left

1. **Related articles have no `data-*` hook** (`RelatedRail.astro` and the "Keep reading" grid) — fine if mOS never touches this surface, painful if it later needs to (e.g. suppressing premium articles from a free reader's related rail — which, separately, is a real content leak today: `getRelatedArticles` doesn't filter by `premium` at all).
2. **CI pins Node 20, local/lockfile assumes Node 22** — not an mOS blocker per se, but worth reconciling before any build-pipeline changes land alongside proxy work, so a future CI run doesn't silently diverge from what was tested locally.
3. **`.env.example`'s "fully static" comment is stale** (app is SSR, not static) — low stakes, but exactly the kind of stale assumption that misleads whoever picks up proxy work next; worth a one-line fix while in the area.
4. **The newsletter form's submission is entirely fake** (`Newsletter.astro`) — if mOS's registration wall is meant to reuse or coexist with this form's UI, know going in that there's no real backend behind it to build on.

### Fine as-is

- **Ad slots** — `[data-ad-slot="<name>"]` is exactly the kind of stable, purpose-built hook mOS needs; zero changes required to detect or strip them for an ad-free experience.
- **Newsletter form detection** (structurally, not its fake submission) — `[data-newsletter]`/`[data-nl-form]` are stable if mOS just needs to find/replace/suppress the form.
- **Bookmark button** — stable selector, not a monetization surface, no action needed.
- **Cache safety of the app's own output** — no cookies set server-side, no `Cache-Control` overrides to fight, no server-side reader-specific branching anywhere outside the always-both-branches Clerk `<Show>` pattern (§6/§8). The origin is about as cache-friendly as an SSR app can be walking into this project; whatever cache-fragmentation risk exists will come from mOS's own personalization step, not from this app.
- **Route surface for interception** — every route is SSR (no prerendering to bypass a proxy/middleware), and there's no client-side router to fight (no `<ClientRouter />`, no `prefetch`) — every navigation is a clean, interceptable full-page HTTP request.

### One Worker vs. two Workers

**Recommendation: two Workers — a separate mOS proxy Worker, service-bound to this one.**

Reasoning, from what's actually in this repo:

- The deployed Worker (`dist/_worker.js/index.js`) is **entirely generated** by the `@astrojs/cloudflare` adapter at build time — there is no hand-written Worker entrypoint in this repo to extend. "Wrapping the proxy around the Astro handler in the same deployment" would mean either (a) post-processing/wrapping the adapter's generated output (fragile — it's regenerated on every build, and nothing in this repo currently does any post-build patching), or (b) forking away from the standard `@astrojs/cloudflare` adapter output path entirely, which is a much bigger lift than "add a proxy."
- Deploys are already a clean, single-purpose pipeline (`.github/workflows/deploy.yml` → `wrangler deploy`) that this team owns and can keep simple. A service-bound proxy Worker gets its own deploy lifecycle, decoupled from Astro/adapter version bumps — meaningful here since `@astrojs/cloudflare` and `astro` both get frequent minor releases (current installed: astro 5.18.2, adapter 12.6.13, both well ahead of the `package.json` `^` floor, implying this repo already tracks upstream fairly actively).
- `wrangler.toml` has zero service bindings, zero multi-Worker structure today — introducing a second Worker with a service binding to this one is a small, additive, easily-reviewed diff to that file, versus surgery on adapter internals.
- Nothing about this app's routing, rendering, or Worker structure requires colocating the proxy in-process — no shared in-memory state, no Durable Objects, nothing that would make a network hop between two Workers meaningfully worse than a function call within one.

### Three questions to answer before writing any proxy code

1. **Where does mOS get its signed-in/entitlement signal from, given this app has no server-side Clerk session read today?** Does mOS's Decision API read Clerk's session cookie itself (needs the exact cookie name/format and a Clerk backend SDK call), or does this app need `clerkMiddleware()` added first so `Astro.locals.auth()` exists for mOS (or the proxy) to consume? This blocks both the paywall decision and the cache-key strategy in §8.
2. **What is the actual free-preview boundary meant to be** — a fixed paragraph count, a percentage of body length, an editorially-set field per article (which doesn't exist in the Sanity schema today, per §7), or something the Decision API computes dynamically? This determines whether `data-mos-block` indices alone are sufficient or whether a new Sanity field is also needed.
3. **What's the caching strategy once mOS starts injecting reader-specific HTML** — fragment the shared cache by decision outcome (free/paywalled/registered — how many buckets?), cache pre-personalization and let `HTMLRewriter` run on every hit even from cache, or don't cache full HTML at all and rely on Sanity/data-layer caching instead? This repo's origin is cache-neutral today (§8) specifically *because* it does none of this — the strategy has to be designed fresh, not inherited.
